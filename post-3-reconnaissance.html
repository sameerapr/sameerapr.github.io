Passive Reconnaissance: What Attackers See

📅 August 27, 2026 ⏱️ 22 min read 🏷️ Beginner 👤 Your Name
#reconnaissance #osint #passive #footprint #cybersecurity
⚠️ EDUCATIONAL DISCLAIMER

All techniques in this post are passive and non-intrusive — they use only publicly available information. These are the same methods attackers use in Stage 1 (Reconnaissance) of the Cyber Kill Chain. Understanding them is essential for defenders who want to reduce their organization's attack surface.

What Is Passive Reconnaissance?

Passive reconnaissance is the art of gathering information about a target without ever interacting with their systems directly. The target has no logs, no alerts, no idea it's happening.

Think of it like researching someone before a job interview — except the "interview" is a cyberattack, and the research reveals every weakness they forgot to hide.

Attackers use passive recon to answer critical questions before making a move:

  • What domains and subdomains does the target own?
  • What technologies power their websites and servers?
  • Who works there, and what are their email formats?
  • What files and documents have been accidentally exposed?
  • What does their network look like from the outside?
📝 Key Distinction

Passive = no packets sent to the target. You only query public databases, search engines, and archives.
Active = direct interaction (port scans, ping sweeps, vulnerability probes). We'll cover active recon in Post #4.

Why Passive Recon Is Invisible (and Dangerous)

Because passive recon never touches the target's infrastructure, there is nothing to log, nothing to alert on, and nothing to block. The information is already public — the attacker is just collecting it.

This makes it the perfect starting point for any attack. By the time an attacker sends their first packet (active recon), they already know:

  • Which employees to phish
  • Which technologies have known vulnerabilities
  • Which subdomains host admin panels or dev environments
  • Which cloud buckets might be misconfigured

For defenders, the goal is simple: reduce what passive recon can find.

Technique 1: WHOIS & DNS Enumeration

Every domain registration leaves a public record. WHOIS databases and DNS servers contain a goldmine of information.

What You Can Learn

Data Point What It Reveals
Registrar Where the domain was purchased
Registration dates How old the domain is (older = more established)
Name servers Which DNS provider they use (Cloudflare, Route53, etc.)
MX records Which email provider they use (Google Workspace, Microsoft 365)
SPF records Which IPs are authorized to send email for the domain
Subdomains Dev environments, admin panels, APIs, staging sites
Historical DNS IP addresses they've used in the past (may reveal infrastructure)

Tools for DNS Enumeration

1. dig (Built into Linux/macOS)

# Query A records (IPv4 addresses)
dig example.com A

# Query MX records (mail servers)
dig example.com MX

# Query TXT records (SPF, DKIM, verification tokens)
dig example.com TXT

# Query NS records (name servers)
dig example.com NS

# Query ALL records
dig example.com ANY

# Use a specific DNS server
dig @8.8.8.8 example.com A

2. nslookup (Built into Windows)

nslookup example.com
nslookup -type=MX example.com
nslookup -type=TXT example.com

3. Online Tools

  • ViewDNS.info — comprehensive DNS lookup, reverse IP, port scan history
  • DNSDumpster — visual DNS map, subdomain discovery
  • SecurityTrails — historical DNS data, domain research

Defensive Countermeasures

Measure How
Private WHOIS Enable privacy protection at your registrar to hide contact details
Minimal DNS exposure Don't list internal subdomains in public DNS; use split-horizon DNS
Clean up old records Remove stale subdomains, dev environments, and test servers from DNS
Monitor for new subdomains Alert when new DNS records appear (could indicate shadow IT or compromise)

Technique 2: Search Engine Dorking (Google Hacking)

Google indexes everything — including things that should never be public. Google Dorks are advanced search operators that find sensitive files, exposed directories, login pages, and more.

Common Dork Operators

Operator Function Example
site: Restrict to a specific domain site:example.com
filetype: Search for specific file types filetype:pdf site:example.com
inurl: Search in URL inurl:admin site:example.com
intitle: Search in page title intitle:"index of" site:example.com
intext: Search in page body text intext:"password" site:example.com
cache: View Google's cached version cache:example.com

Dangerous Dorks (What Attackers Search For)

⚠️ Only Search Your Own Domains

These dorks are powerful. Use them only on domains you own or have permission to test. Searching other people's systems without authorization may violate terms of service and local laws.

Dork What It Finds
site:example.com filetype:pdf All PDFs — may contain sensitive reports, proposals, or internal docs
site:example.com filetype:xls OR filetype:csv Spreadsheets — potential customer lists, financial data
site:example.com intitle:"index of" Open directory listings — exposed files without authentication
site:example.com inurl:login OR inurl:admin Login pages — potential brute-force targets
site:example.com intext:"password" OR intext:"secret" Pages containing sensitive keywords
site:example.com filetype:env OR filetype:config Configuration files — may contain API keys, database credentials
site:example.com ext:sql SQL dump files — potential database backups
site:example.com intitle:"phpinfo()" Exposed PHP info pages — reveal server configuration

Defensive Countermeasures

  • Robots.txt + noindex — Prevent search engines from indexing sensitive directories (but don't rely on this alone — robots.txt is public)
  • Authentication — Every admin panel, dev environment, and internal tool must require login
  • File access controls — Don't store sensitive files in web-accessible directories
  • Regular audits — Search your own domain with dorks monthly to find leaks
  • Google Search Console — Use "Remove URLs" tool to de-index exposed content quickly

Technique 3: Shodan & Censys — The Search Engine for Everything

While Google indexes websites, Shodan and Censys index internet-connected devices: servers, routers, webcams, industrial control systems, databases, and more.

What Shodan Reveals

  • Open ports and running services
  • Server software and versions (Apache 2.4.41, nginx 1.18.0)
  • SSL certificate details
  • Geographic location of servers
  • Default credentials still in use
  • IoT devices, cameras, printers exposed to the internet

Basic Shodan Queries

# Search by hostname
hostname:example.com

# Search by IP
ip:192.168.1.1

# Search for specific service
apache

# Search for specific version (vulnerable?)
apache 2.4.49

# Search for specific port
port:3389  # RDP

# Search for specific country
country:US port:445  # SMB in the US

# Search for default pages
title:"Apache2 Ubuntu Default Page"

Censys — The Alternative

Censys provides similar data with a focus on certificates and hosts. It's excellent for:

  • Certificate transparency logs (discover subdomains from SSL certs)
  • IPv4 host scanning with service banners
  • Historical data on how a host has changed over time

Defensive Countermeasures

Measure How
Firewall default-deny Only expose ports that absolutely must be public
Change default banners Hide server versions in HTTP headers and service banners
Monitor your exposure Create free Shodan/Censys accounts and set up alerts for your IPs
VPN for management Never expose RDP, SSH, or admin panels directly to the internet
Disable unnecessary services If you don't need it, don't run it — and certainly don't expose it

Technique 4: OSINT on People (Social Engineering Prep)

People are often the weakest link. Attackers research employees to craft convincing phishing emails, impersonation attacks, or pretexting phone calls.

What Attackers Look For

Source Intelligence Gathered
LinkedIn Job titles, reporting structure, technologies used, project names, email formats
Company Website Team pages, press releases, job postings (reveal technologies and internal systems)
GitHub Code repositories, commit history (may expose credentials, internal URLs, API keys)
Pastebin / GitHub Gists Accidentally leaked code, config files, credentials
Social Media Personal details for password guessing, security question answers, travel schedules
Data Breach Databases Previously leaked credentials that may be reused (Have I Been Pwned)

Email Format Discovery

Once an attacker knows one employee's email format, they can guess everyone's:

  • firstname.lastname@company.com
  • flastname@company.com
  • firstinitiallastname@company.com

Tools like theHarvester and Hunter.io automate this discovery.

Defensive Countermeasures

  • Limit public employee directories — Don't list full names, titles, and photos publicly
  • Generic email formats — Avoid predictable patterns; use random IDs for public-facing addresses
  • Job posting hygiene — Don't list specific internal technologies, software versions, or architecture details
  • GitHub monitoring — Use tools like GitGuardian or TruffleHog to scan for leaked secrets
  • Employee training — Teach staff what information is valuable to attackers and how to limit sharing
  • Breach monitoring — Subscribe to Have I Been Pwned domain alerts to know when employee emails appear in breaches

Technique 5: Wayback Machine & Cached Content

The Internet Archive's Wayback Machine stores historical snapshots of websites. Attackers use it to see old versions of sites that may have exposed sensitive information before being cleaned up.

What Attackers Find

  • Old admin panels or login pages that have since been moved
  • Deleted pages that contained technical details
  • Previous versions of the site with known vulnerabilities
  • Robots.txt files that revealed hidden directories
  • Exposed configuration files or backup pages

How to Use It (For Defense)

# Visit: https://web.archive.org/web/*/example.com
# Browse historical snapshots
# Look for pages that should not have been public

Defensive Countermeasures

  • Request removal — Email archive.org to remove sensitive historical snapshots
  • Think before publishing — Once something is on the internet, it may be archived forever
  • Regular checks — Search your domain on Wayback Machine quarterly

Technique 6: Certificate Transparency Logs

Every time an organization requests an SSL/TLS certificate, it's logged in public Certificate Transparency (CT) logs. These logs reveal subdomains that might not appear in DNS.

Tools for CT Log Enumeration

  • crt.sh — Free web interface to search CT logs
  • Censys — Certificate-based host discovery
  • Certificate Transparency Monitoring — Facebook, Google, and Cloudflare offer monitoring tools

What Attackers Discover

A certificate for staging-api.example.com might not have a public DNS record, but it exists in CT logs. Attackers now know there's a staging environment to probe.

Defensive Countermeasures

  • Monitor your own CT logs — Set up alerts for new certificates issued for your domain
  • Use wildcard certificates — A single *.example.com cert doesn't reveal individual subdomains
  • Protect staging environments — Even if discovered, staging should be behind VPN or IP allowlisting

Hands-On Exercise: Audit Your Own Digital Footprint

Let's put these techniques into practice — on your own systems or a test domain you control.

Exercise 1: DNS Reconnaissance

  1. Pick a domain you own (or use a test domain)
  2. Run these commands from your Kali VM:
# Basic DNS lookup
dig example.com ANY

# MX records (email infrastructure)
dig example.com MX

# TXT records (SPF, DKIM, verification tokens)
dig example.com TXT

# Use DNSDumpster online for visual subdomain map
# Visit: https://dnsdumpster.com

Questions to answer:

  • What name servers are you using?
  • Are there any subdomains you forgot about?
  • Does your SPF record reveal internal IP ranges?
  • Are there old TXT records with verification tokens still present?

Exercise 2: Google Dorking Self-Audit

  1. Open Google in a private/incognito window
  2. Search your domain with these dorks (replace example.com):
site:example.com filetype:pdf
site:example.com filetype:xls OR filetype:csv
site:example.com intitle:"index of"
site:example.com inurl:admin OR inurl:login
site:example.com filetype:env OR filetype:config

Questions to answer:

  • Did you find any files that shouldn't be public?
  • Are there directory listings exposing file structures?
  • Are there old login pages or admin panels still accessible?

Exercise 3: Shodan Exposure Check

  1. Create a free account at shodan.io
  2. Search for your public IP address
  3. Review what services and ports are visible

Questions to answer:

  • Are there any services exposed that you didn't know about?
  • Does Shodan show software versions that are outdated?
  • Are there any default pages or banners revealing too much?
🛡️ Defensive Takeaway

The goal of this exercise is not to find vulnerabilities — it's to understand what an attacker can see without ever touching your systems. Every piece of information you reduce is one less tool in the attacker's arsenal.

Building a Passive Recon Defense Checklist

Area Action Frequency
WHOIS Enable privacy protection; verify contact info is current Annually
DNS Audit all records; remove stale entries; monitor for changes Quarterly
Google Dorks Search your domain with common dorks; remove exposed content Monthly
Shodan/Censys Search your IPs; set up exposure alerts; close unnecessary ports Monthly
CT Logs Monitor for new certificates; use wildcards where possible Continuous (alerts)
Wayback Machine Check historical snapshots; request removal of sensitive content Quarterly
GitHub/OSINT Scan for leaked credentials; monitor employee social media exposure Monthly
Data Breaches Subscribe to Have I Been Pwned domain alerts; force password resets Continuous (alerts)

Summary: The Attacker's View vs. The Defender's View

Technique Attacker Sees... Defender Should...
DNS/WHOIS Infrastructure map, email provider, name servers Minimize records, use privacy protection, clean stale entries
Google Dorks Exposed files, directory listings, login pages Regular self-audits, proper access controls, de-index leaks
Shodan/Censys Open ports, service versions, exposed devices Firewall hardening, version hiding, exposure monitoring
OSINT on People Email formats, org chart, technologies, personal details Limit public directories, train employees, monitor leaks
Wayback Machine Old pages, deleted content, previous vulnerabilities Request removals, think before publishing sensitive info
CT Logs Hidden subdomains, certificate history Use wildcards, monitor new certs, protect discovered assets
