Active Scanning with Nmap

📅 September 3, 2026 ⏱️ 28 min read 🏷️ Beginner 👤 Your Name
#nmap #scanning #network #reconnaissance #cybersecurity
⚠️ EDUCATIONAL DISCLAIMER

Nmap is a legitimate network security scanner used by millions of professionals worldwide. However, scanning networks you do not own or have explicit written permission to test is illegal in most jurisdictions. This guide covers Nmap from both offensive and defensive perspectives. All exercises should be performed only in your isolated lab environment from Post #1.

From Passive to Active

In Post #3, we covered passive reconnaissance — gathering intelligence without ever touching the target's systems. Now we cross the line into active reconnaissance: sending packets directly to the target and analyzing the responses.

This is where things get real. Active scanning generates logs, triggers alerts, and can be detected by intrusion detection systems. It's also where most attackers begin their technical engagement — and where defenders have their first real opportunity to spot an intruder.

Nmap (Network Mapper) is the gold standard for active network scanning. Created by Gordon Lyon (Fyodor) in 1997, it's free, open-source, and installed by default on Kali Linux. Over 25 years of development have made it the most powerful and flexible port scanner in existence.

📝 Key Distinction

Passive recon = no packets to target, completely invisible.
Active scanning = packets sent to target, detectable and loggable. This is Stage 1 (Reconnaissance) of the Kill Chain turning technical.

How Port Scanning Works

Before diving into Nmap commands, you need to understand what happens under the hood when you scan a port.

The TCP Three-Way Handshake

TCP (Transmission Control Protocol) requires a three-step handshake to establish a connection:

Step Packet Flag Meaning
1 Client → Server SYN "I want to connect"
2 Server → Client SYN-ACK "I received your request, I'm ready"
3 Client → Server ACK "Acknowledged, connection established"

Nmap exploits this handshake (and deviations from it) to determine port states.

Port States

State What It Means Security Implication
open Service is listening and accepting connections Potential attack surface — investigate the service
closed Port is accessible but no service is listening Less risk, but still visible to attackers
filtered Nmap can't determine state — likely blocked by firewall Good defense, but reveals firewall presence
unfiltered Port is accessible but Nmap can't determine open/closed Rare, usually seen with ACK scans
open|filtered Nmap can't distinguish between open and filtered Common with UDP scans or FIN/NULL/Xmas scans
closed|filtered Nmap can't distinguish between closed and filtered Rare, seen with certain IDS evasion scans

Nmap Basics: Your First Scans

Open a terminal on your Kali VM (from Post #1) and ensure your Windows target VM is running on the isolated Lab-Network.

Scan 1: Simple Ping Sweep

Before scanning ports, confirm the target is online.

# Ping scan — check if host is up (no port scanning)
nmap -sn 192.168.56.20

# Ping sweep a range of IPs
nmap -sn 192.168.56.1-254

# Alternative: ARP ping (more reliable on local networks)
nmap -sn -PR 192.168.56.20

Output explained:

  • Host is up (0.00045s latency) — target responded to ping
  • MAC Address: 08:00:27:xx:xx:xx — VirtualBox virtual NIC identifier

Scan 2: Default Port Scan

Nmap's default scan checks the top 1,000 most common ports.

# Default scan (top 1000 TCP ports)
nmap 192.168.56.20

# Scan with verbosity
nmap -v 192.168.56.20

What happens: Nmap sends SYN packets to each port. If it receives SYN-ACK, the port is open. If it receives RST, the port is closed. If nothing comes back, it's filtered.

Scan 3: Scan All Ports

There are 65,535 TCP ports. The default 1,000 covers the most common services, but malware and custom apps often hide on high ports.

# Scan all 65535 TCP ports (slow but thorough)
nmap -p- 192.168.56.20

# Scan specific ports
nmap -p 22,80,443,3389 192.168.56.20

# Scan a port range
nmap -p 1-1000 192.168.56.20
⚠️ Time Warning

Scanning all 65,535 ports can take 30+ minutes per host. In a real engagement, start with the top 1,000, then expand based on findings. In your lab, feel free to run full scans to see the difference.

Nmap Scan Types: The Complete Toolkit

Nmap offers multiple scan types, each with different speed, stealth, and reliability characteristics. Understanding them is essential for both attackers and defenders.

1. TCP Connect Scan (-sT)

Completes the full three-way handshake on every port. The most reliable but also the noisiest and slowest.

# TCP Connect scan
nmap -sT 192.168.56.20
Pros Cons
Works on all systems (no raw packet privileges needed) Very noisy — full handshake logged by target
Most accurate and reliable Slower than SYN scan
Can scan through proxies Easily detected by IDS/IPS

2. SYN Stealth Scan (-sS) — The Default

Sends SYN, waits for SYN-ACK, then sends RST instead of completing the handshake. Faster and stealthier than connect scan.

# SYN stealth scan (default when run as root)
sudo nmap -sS 192.168.56.20
Pros Cons
Faster than connect scan (half-open) Requires root/admin privileges (raw packets)
Stealthier — no full connection logged Still detectable by modern IDS
Default and most commonly used Some firewalls block incomplete handshakes

3. UDP Scan (-sU)

UDP is connectionless — no handshake. Nmap sends UDP packets and interprets ICMP responses or lack thereof.

# UDP scan (very slow — use top ports)
sudo nmap -sU --top-ports 100 192.168.56.20

# UDP scan specific ports
sudo nmap -sU -p 53,67,68,123,161,500 192.168.56.20
Pros Cons
Finds UDP services (DNS, DHCP, SNMP, NTP) Extremely slow (no response = timeout)
Often overlooked by defenders Many results show as open|filtered
Critical for comprehensive assessment Requires root privileges

4. FIN, NULL, and Xmas Scans (-sF, -sN, -sX)

These send malformed packets to exploit differences in RFC compliance between operating systems. Named because the Xmas scan sets FIN, PSH, and URG flags — "lighting up the packet like a Christmas tree."

# FIN scan
sudo nmap -sF 192.168.56.20

# NULL scan (no flags set)
sudo nmap -sN 192.168.56.20

# Xmas scan
sudo nmap -sX 192.168.56.20
Pros Cons
Can bypass simple firewalls that only block SYN Only works reliably against Unix/Linux targets
Stealthy against basic logging Windows always responds RST (all ports show closed)
Interesting for OS fingerprinting Easily detected by modern IDS

5. ACK Scan (-sA)

Sends ACK packets to map firewall rulesets. Doesn't determine open/closed ports, but reveals whether ports are filtered or unfiltered.

# ACK scan — map firewall rules
sudo nmap -sA 192.168.56.20

6. Window Scan (-sW) and Maimon Scan (-sM)

Niche scans that exploit specific TCP window size behaviors in certain operating systems. Rarely used in practice but good to know they exist.

Scan Type Comparison Table

Scan Type Flag Speed Stealth Best For
TCP Connect -sT Slow Low When you lack root access
SYN Stealth -sS Fast Medium Default choice for most scans
UDP -sU Very Slow Medium Finding UDP services
FIN/NULL/Xmas -sF/-sN/-sX Medium Medium Bypassing simple firewalls (Linux targets)
ACK -sA Fast Medium Firewall rule mapping

Service Detection & Version Scanning

Finding an open port is only the beginning. Knowing what service is running and what version tells you whether it's vulnerable to known exploits.

Service Version Detection (-sV)

# Detect service versions on open ports
nmap -sV 192.168.56.20

# Aggressive version detection (more accurate, slower)
nmap -sV --version-intensity 5 192.168.56.20

# Light version detection (faster, less accurate)
nmap -sV --version-intensity 0 192.168.56.20

Output example:

PORT     STATE SERVICE       VERSION
135/tcp  open  msrpc         Microsoft Windows RPC
139/tcp  open  netbios-ssn   Microsoft Windows netbios-ssn
445/tcp  open  microsoft-ds  Windows 10 Pro 19045 microsoft-ds
3389/tcp open  ms-wbt-server Microsoft Terminal Services

OS Detection (-O)

Nmap sends a series of crafted TCP and UDP packets, then compares the responses against a database of known OS fingerprints.

# Operating system detection
sudo nmap -O 192.168.56.20

# Limit OS detection to one guess (faster)
sudo nmap -O --osscan-limit 192.168.56.20

Output example:

Running: Microsoft Windows 10|2016|2019
OS CPE: cpe:/o:microsoft:windows_10
OS details: Microsoft Windows 10 1903 - 2004
💡 Pro Tip

Combine scans for efficiency: sudo nmap -sS -sV -O 192.168.56.20 runs SYN stealth scan + version detection + OS fingerprinting in one pass.

The Nmap Scripting Engine (NSE)

NSE is one of Nmap's most powerful features. It allows Nmap to run Lua scripts that perform vulnerability detection, malware hunting, information gathering, and more.

How NSE Works

NSE scripts are organized into categories:

Category Purpose Example Scripts
safe Non-intrusive, won't crash services banner, ssh-hostkey
intrusive May crash services or trigger alerts mysql-empty-password, ftp-anon
vuln Check for specific vulnerabilities smb-vuln-ms17-010, http-shellshock
exploit Attempt to exploit vulnerabilities ftp-vsftpd-backdoor
auth Test authentication mechanisms ssh-auth-methods, mysql-empty-password
discovery Learn more about the target snmp-sysdescr, dns-service-discovery
dos May cause denial of service Use with extreme caution

Essential NSE Scripts

# Run all safe scripts
nmap -sV --script=safe 192.168.56.20

# Run vulnerability checks
nmap -sV --script=vuln 192.168.56.20

# Check for specific vulnerability (EternalBlue)
nmap -sV --script=smb-vuln-ms17-010 192.168.56.20

# Check for default or empty passwords
nmap -sV --script=auth 192.168.56.20

# Grab service banners
nmap -sV --script=banner 192.168.56.20

# Run a specific script
nmap -sV --script=http-title 192.168.56.20

# Run multiple scripts
nmap -sV --script=http-title,ssh-hostkey,banner 192.168.56.20

# List all available scripts
ls /usr/share/nmap/scripts/ | less

# Get script help
nmap --script-help=smb-vuln-ms17-010

NSE Script Example: SMB Vulnerability Scan

SMB (Server Message Block) is a common Windows file-sharing protocol with a history of critical vulnerabilities. Let's scan for them:

# Scan for common SMB vulnerabilities
nmap -p 445 --script=smb-vuln-ms17-010,smb-vuln-ms08-067,smb-os-discovery 192.168.56.20

# Full SMB enumeration
nmap -p 445 --script=smb-enum-shares,smb-enum-users,smb-os-discovery 192.168.56.20

What this reveals:

  • Whether the target is vulnerable to EternalBlue (MS17-010)
  • Whether the target is vulnerable to Conficker (MS08-067)
  • Windows version and domain information
  • Available network shares
  • User accounts (if accessible)
⚠️ Script Safety

Always check a script's category before running it. Scripts marked intrusive, exploit, or dos can crash services or cause outages. In your lab, experiment freely. In production, only run safe scripts without explicit authorization.

Timing & Performance Tuning

Nmap scans can be slow. Understanding timing options helps you balance speed against stealth and accuracy.

Timing Templates (-T0 to -T5)

Template Name Speed Use Case
-T0 Paranoid One port every 5+ minutes IDS evasion (extremely slow)
-T1 Sneaky One port every 15 seconds IDS evasion (very slow)
-T2 Polite 10x slower than default Low bandwidth, avoid detection
-T3 Normal Default speed Standard scanning
-T4 Aggressive Fast, assumes reliable network Lab environments, CTFs
-T5 Insane Very fast, may miss ports Quick sweeps on local networks 
# Aggressive scan for lab/CTF use
nmap -T4 192.168.56.20

# Polite scan to avoid overwhelming the target
nmap -T2 192.168.56.20

# Insane speed for quick host discovery
nmap -T5 -sn 192.168.56.0/24

Other Performance Options

# Parallelism: scan more hosts/ports simultaneously
nmap --min-parallelism 100 192.168.56.20

# Host timeout: don't waste time on unresponsive hosts
nmap --host-timeout 30s 192.168.56.0/24

# Max retries: reduce retries for faster scans
nmap --max-retries 1 192.168.56.20

# Combine for fast CTF-style scanning
nmap -T4 --max-retries 1 --host-timeout 30s -p- 192.168.56.20

Output Formats: Saving Your Results

Nmap supports multiple output formats. Saving results is critical for documentation, reporting, and comparison over time.

Output Options

Flag Format Best For
-oN Normal text Human reading, quick notes
-oX XML Importing into tools (Metasploit, parsers)
-oG Grepable Scripting, grep, awk processing
-oA All formats Saves .nmap, .xml, and .gnmap at once 
# Save in all formats
nmap -sV -O 192.168.56.20 -oA scan-results

# This creates:
# scan-results.nmap  (human readable)
# scan-results.xml   (machine readable)
# scan-results.gnmap (grepable)

# View normal output
cat scan-results.nmap

# Extract open ports from grepable output
cat scan-results.gnmap | grep "Ports:"

The Defender's Perspective: Detecting Nmap Scans

Now that you know how Nmap works, let's flip the table. How do you detect when someone is scanning your network?

1. IDS/IPS Signatures

Intrusion Detection Systems like Snort and Suricata have built-in rules for detecting port scans:

  • Too many SYN packets to different ports from one source in a short time
  • Incomplete handshakes (SYN without ACK) — signature of SYN scans
  • Malformed packets (FIN, NULL, Xmas) — these are not normal traffic
  • Sequential port probing — natural traffic is random; scans are ordered

2. Firewall Logs

Even if a scan doesn't trigger an IDS alert, your firewall logs every dropped packet. A spike in blocked connection attempts from a single IP is a clear indicator.

3. Honeypots

Deploy fake services (honeypots) on your network. Any connection to them is suspicious by definition — no legitimate user should ever touch them. Tools like Cowrie (SSH honeypot) or T-Pot (multi-honeypot platform) can detect and analyze scanning behavior.

4. Network Flow Analysis

NetFlow or Zeek (formerly Bro) records metadata about all network connections. Analyzing flows reveals:

  • A single source IP connecting to hundreds of destination ports
  • Short-duration connections (SYN scans complete in milliseconds)
  • Connections at unusual times or from unusual geographic locations

5. Host-Based Detection

On the target machine itself:

  • Windows Event Logs — Security log records failed logins, but not port scans directly
  • Sysmon — Can log network connections by process, helping identify scan responses
  • TCPView / netstat — Show unusual connection patterns in real-time

Sample Snort Rule for SYN Scan Detection

# Detects multiple SYN packets without completing handshake
alert tcp any any -> $HOME_NET any (msg:"NMAP SYN Scan Detected";
    flags:S; threshold:type both, track by_src, count 20, seconds 60;
    sid:1000001; rev:1;)

This rule triggers when a single source sends 20+ SYN packets within 60 seconds — classic scan behavior.

Evasion vs. Detection: The Arms Race

Attacker Technique Defender Counter
Fast scan (-T5) Rate limiting, connection throttling
Slow scan (-T0) Long-term flow analysis, anomaly detection
Fragmented packets (-f) Reassembly at firewall/IDS, deep packet inspection
Decoy scans (-D) Correlation analysis, geolocation filtering
Randomized order (--randomize-hosts) Statistical analysis of connection patterns
Source port spoofing (--source-port) Stateful firewall inspection, asymmetric routing detection

Hands-On Exercise: Comprehensive Lab Scan

Let's put everything together in your isolated lab. Ensure both Kali and Windows VMs are running on the Lab-Network.

Exercise 1: Basic Discovery

# 1. Confirm target is online
nmap -sn 192.168.56.20

# 2. Default port scan
nmap 192.168.56.20

# 3. Save results
nmap 192.168.56.20 -oA basic-scan

# 4. Review the output
cat basic-scan.nmap

Questions:

  • How many ports are open?
  • Which ports did you expect to see on a Windows machine?
  • Are there any unexpected open ports?

Exercise 2: Service & OS Detection

# 1. Version and OS detection
sudo nmap -sS -sV -O 192.168.56.20 -oA detailed-scan

# 2. Review service versions
cat detailed-scan.nmap | grep -E "(PORT|open)"

# 3. Check if any services are outdated
# Compare versions against CVE databases (cve.mitre.org)

Questions:

  • What Windows version did Nmap guess?
  • How accurate was the OS fingerprint?
  • Are any service versions known to have vulnerabilities?

Exercise 3: NSE Vulnerability Scan

# 1. Run safe vulnerability checks
nmap -sV --script=vuln 192.168.56.20 -oA vuln-scan

# 2. Specifically check SMB
nmap -p 445 --script=smb-vuln-ms17-010,smb-os-discovery 192.168.56.20

# 3. Check for common misconfigurations
nmap -sV --script=banner,http-title,ssh-hostkey 192.168.56.20

Questions:

  • Did any vulnerability scripts report findings?
  • What information do banners reveal?
  • Would an attacker find anything useful here?

# Time a connect scan
time nmap -sT 192.168.56.20

# Time a SYN scan
time sudo nmap -sS 192.168.56.20

# Time with aggressive timing
time sudo nmap -sS -T4 192.168.56.20

# Check Windows firewall logs after each scan
# (Event Viewer → Windows Logs → Security)

Questions:

  • Which scan was fastest?
  • Did the Windows firewall log any of the scans?
  • How much difference did timing template make?

🛡️ Defensive Takeaway

Every scan you performed generated network traffic that could have been logged and alerted on. As a defender, your job is to ensure those logs exist, the alerts fire, and the response playbook is ready. As an attacker, your job is to evade those controls. Understanding both sides makes you a better security professional.
